# Direct rich local native presentation v2

Selected source-preparation mapping, not runtime/native/provider acceptance.
The Core Direct rich HTTP profile remains djconnect-direct-rich-v1 and its
closed frame/schema are unchanged. This separately versioned LOCAL native
presentation is for the SAME existing Session Activity attributes/ContentState
alias, widget and renderer; no second Activity, push-to-start or new setting.

The complete original Direct frame, purpose, field rights and reference graph
stay separately typed in actual client RAM custody. Native presentation DATA
is never an original permission envelope or replacement clock witness.

An optional typed research-attribution field INSIDE rich binds all original
sources and expression_license to exactly the same contribution/moment. Its
encoder, closed preflight and actual renderer must preserve every required
source URL/revision/provider/licence and adaptation notice. Never silently
decode only the old Contribution fields, retain just the first attribution,
flatten references to a new undocumented string, summarize or truncate to fit.

Compiled local profile identifier: `djconnect-session-rich-direct-local-v2`.
The serialized rich object has required `directLocalVersion`: exact integer2
(not Boolean/float/string). This marker is DATA only and cannot select permission
or an API transport. Optional `researchAttribution` is a closed object with
exact keys `momentID`, `sources`, `expressionLicense`. momentID equals the actual
same contribution's original moment_id; no contribution means no attribution.
Sources preserve the Direct frame's exact source keysets, values, ordering and
all original revision URLs. expressionLicense preserves the exact existing
`id`, `url`, `adapted`, `attribution_required` fields from expression_license.
The real renderer shows every required source/revision/provider/license and
adaptation attribution; unknown/missing keys or mismatched moment close only
that unsupported contribution. No arbitrary string-dictionary side channel.

Only the explicit direct-local-v2 encoder/validator may emit/accept these two
new rich keys. Even without research, v2 emits directLocalVersion=2. Legacy
encoding leaves BOTH optional properties nil/absent and preserves the old shape;
researchAttribution without the v2 marker is rejected, never treated as v1.
The actual native payload type stays the same existing Activity alias; the
version marker does not create or adopt a native Activity or restore custody.

The entire encoded rich INCLUDING research attribution stays <=2800 UTF8 bytes;
actual serialized attributes+complete ContentState stays <=4096. Metadata cannot
be moved outside rich to evade the cap. If required content/attribution does
not fit or the real renderer cannot preserve it, mark only that contribution
locally representation_not_supported and clear its old slot. Preserve separately
qualified current playback and its exact eligible artwork. Do not rewrite the
original Core frame's source qualification, source times or reference graph.

Frozen djconnect-session-rich-v1 DATA carrier/preflight/relay stays byte-frozen
and rejects the new extra native field. It is not reinterpreted as v2. The new
direct-local encoder/validator is selected by an explicit compiled local profile
and actual original client custody, not a request-provided format switch.
Original native fixture bytes and their digests stay unchanged. Compare the old
and new model with BOTH optional fields nil under the SAME explicit encoder
configuration as separate compatibility evidence. A sorted-key re-encoding must
not replace a default-encoder original or be claimed as proof that arbitrary
default JSONEncoder output is byte-deterministic. Causal checks must show v1 rejects v2, v2 preserves all
research data and actual rendering, and exact2800/4096 boundary behavior.

No external_relay permission, API rich-profile admission, APNs content transport
or provider/key effect follows. API's separately admitted content-free host-app
wake and the genuine DIRECT Core read remain the selected transport. Native
original clock/once, initial permission before SDK, real returned Activity handle,
withdrawal and final cache/image/SDK currentness guards remain independently
required. No legacy Activity inventory is automatically adopted or restarted.

Apple owns the complete client HTTP/custody/staging/renderer composition and its
whole/exact reviews, normal Source/separate Final delivery. This mapping is not
a separate DATA-only feature release or a claim that the integration is done.
